# DiskCC · Windows C 盘智能清理工具

内置规则库 + 可选 AI 识别的 C 盘清理工具。既覆盖「临时文件 / Windows 更新缓存 / 浏览器缓存」等常规垃圾，
也能**识别 `Program Files` 里每个文件夹属于哪个软件**、**分析 `AppData` 中每个目录的作用并挑出可以放心清理的文件**。

> 定位：先「看得懂再删」。所有项目都带作用说明、风险等级与识别来源（规则库 / 注册表 / 文件版本信息 / AI），
> 默认只勾选最安全的项目，其余由你手动确认。

---

## 一、快速开始

### 方式 A：源码运行（需 Python 3.9+，推荐 3.11）

```bat
pip install -r requirements.txt
python main.py
```

### 方式 B：打包成单文件 exe（无 Python 环境的电脑也能用）

```bat
build_exe.bat
```

生成**单个文件** `dist\DiskCC.exe`（自包含，可直接发给任何 Windows 电脑，无需安装 Python、也无需附带任何文件夹）。
打包时带 `--uac-admin`，双击即请求管理员权限。
> 清理 `C:\Windows\Temp`、`SoftwareDistribution`、执行 DISM/powercfg 等必须管理员权限。
> 未提权也能运行，只是这些项目会失败并提示。

v1.2.0 起打包走 `DiskCC.spec`（精简 Qt 组件、禁用 UPX、写入 exe 版本资源），并在 `dist\DiskCC.exe.sha256.txt`
生成 SHA256 校验值，便于接收方验签与加入杀软白名单。详见 **八、常见问题 → 关于杀毒软件误报**。

### 命令行模式（不启动界面，适合定时任务/排障）

```bat
python main.py --cli --out report.csv
python main.py --cli --min-size 5 --out result.json
python main.py --selftest          :: 构造模拟 C 盘跑通扫描引擎（自测）
python main.py --admin             :: 以管理员权限重新启动
```

## 三、AI 识别怎么用

**没有 API Key 也能完整使用**：内置知识库包含数百条软件映射（`Program Files` 目录名 → 软件）、
一百余条 AppData 目录规则、几十条通用缓存目录名规则，配合注册表安装记录与 PE 文件版本信息，
绝大多数目录都能离线判定。AI 只用于处理规则库拿不到的部分。

开启方式：界面【⚙ 设置 → AI 识别】，或手动编辑配置：

```jsonc
{
  "ai_enabled": true,
  "ai_base_url": "https://api.deepseek.com/v1",
  "ai_api_key": "sk-xxxx",
  "ai_model": "deepseek-chat"
}
```

* 兼容任意 **OpenAI 格式**接口：DeepSeek、通义千问（兼容模式）、智谱 GLM、Kimi、OpenAI、本地 Ollama 等，设置页有预设。
* 点【测试连接】可验证配置。
* **上传内容只有元信息**：目录名、大小、文件数、子目录名、可执行文件名、PE 里的 ProductName/CompanyName，
  **不包含任何文件内容、不含你的文档与个人信息**。
* 结果会本地缓存（默认 30 天，路径 `%LOCALAPPDATA%\DiskCC\ai_cache.json`），同样的目录不会重复花钱。
* 可勾选「只对规则库无法识别的目录调用 AI」以省钱提速（默认开启）。

## 四、Program Files 归属识别逻辑

按可信度从高到低依次尝试，命中即停止：

1. **注册表**：读取 `Uninstall` 项的 `InstallLocation / DisplayName / Publisher`，与目录做精确、父子关系匹配 → 判定「已安装」，风险=危险（不删，可右键启动卸载程序）。
2. **内置规则库**：数百条「目录名 → 软件名」映射（含版本后缀与前缀模糊匹配），例如 `7-Zip → 7-Zip`、`Adobe Photoshop 2024 → Adobe Photoshop`、`WeChat → 微信`。
3. **PE 文件版本信息**：无第三方依赖地解析目录内 `.exe/.dll` 的 `VS_VERSION_INFO`，取 `ProductName / CompanyName / FileDescription`（纯 Python 实现，`diskcc/utils/pever.py`）。
4. **启发式**：有无可执行文件、子目录数量、最后修改时间 → 区分「厂商容器目录（如 Adobe）」与「卸载残留」。
5. **AI 兜底**：批量提交未识别目录，返回 `归属软件 / 作用 / 已安装·残留·组件 / 是否可删 / 风险 / 置信度`，置信度 ≥0.7 且判定可删才会自动勾选。

结论在表格「归属软件」「来源」「说明」三列直接可见：来源为 `规则库 / 注册表 / 文件信息 / AI`。

## 五、AppData 分析逻辑

* **已知路径表**：Chrome/Edge 各级缓存、Explorer 缩略图、WER、pip/npm 等直接命中为「可放心清理」。
* **规则库**：`WeChat → 微信（聊天图片、文件缓存与配置）`、`SomeGame → 游戏` 等，并给出是否可整目录清理。
* **通用缓存目录名**：任意软件目录下出现 `Cache / Code Cache / GPUCache / ShaderCache / logs / Crashpad / temp / Service Worker / blob_storage / Session Storage / …` 一律判定为可放心清理的缓存，且**不再下潜**（避免重复统计）。
* **是否仍在用**：结合注册表安装记录判断目录是否为「软件卸载后的残留」；只有同时满足「未安装」+「超过设定天数（默认 90 天）未更新」才标为残留。
* **AI**：对规则库未收录且体积较大的目录，批量询问「存放什么数据 / 缓存还是配置 / 能否删除 / 风险」。
* **大体积日志文件**：AppData 根下 ≥20MB 的 `.log/.dmp/.tmp/.bak/.etl` 等文件会被单独列出。

**可以放心清理的（默认已勾选，风险=安全/低风险）**：各类 `Cache*`、`Code Cache`、`GPUCache`、着色器缓存、
`logs`、`Crashpad/CrashDumps`、`temp`、浏览器各类缓存、包管理器缓存、Adobe 媒体缓存、Teams 媒体缓存、
Steam 着色器缓存、AppData 根下的大日志文件等——这些删除后软件会自动重建，不影响账号、配置与个人数据。

**不会自动勾选**：含配置/登录态/聊天记录/笔记/工程数据的目录（风险=中等），以及 Program Files 中判定为「已安装」的程序目录（风险=危险，请走卸载程序）。

## 六、安全机制

| 机制 | 说明 |
|---|---|
| 保守默认 | 只有风险等级为「安全/低风险」的项目默认勾选；高风险与命令类项目必须手动勾选 |
| 系统路径黑名单 | `System32 / SysWOW64 / WinSxS / Boot / Fonts / WindowsApps` 等一律禁止删除 |
| Windows 子目录保护 | `C:\Windows` 的直接子文件夹默认不列为清理项（仅 `Temp`/`SoftwareDistribution`/`Prefetch`/`Logs`/`Minidump` 等白名单可清理），避免误删系统关键目录 |
| 允许根校验 | 清理路径必须落在系统盘、用户目录、AppData、ProgramData、Program Files 等允许范围内 |
| 回收站优先 | 默认走回收站（可还原），关闭后才是永久删除 |
| 备份清单 | 每次清理前把完整清单写到 `%LOCALAPPDATA%\DiskCC\clean_logs\` |
| 演练模式 | 设置里可开启「只报告不删除」 |
| 排除列表 | 右键某行 → 加入排除列表，后续扫描跳过该路径 |
| 占用保护 | 跳过 24 小时内修改过的临时文件与被进程占用的文件 |
| 危险项拦截 | 风险=危险的项目（已安装程序）直接拒绝删除，并提示改用卸载程序 |

## 八、常见问题

**Q：为什么有些项目删不掉？**
A：多为权限不足或文件被占用。请以管理员身份运行；浏览器、微信等软件退出后重试；`Windows.old` 若失败请用
【设置 → 系统 → 存储 → 临时文件 → 以前的 Windows 安装】清理。

**Q：清理会不会影响已安装的软件？**
A：默认勾选的只有缓存类项目，删除后软件会自动重建。Program Files 中判定为「已安装」的目录风险等级为「危险」，
程序会拒绝删除并建议你走卸载程序。

**Q：AI 会不会把我的文件内容传出去？**
A：不会。只发送目录名、大小、文件数、子目录名、可执行文件名等元信息，不发送文件内容、文档、聊天记录或个人信息。

**Q：扫描很慢？**
A：v1.2.0 起默认开启**并行扫描**（多类目录同时扫描，机械硬盘收益最大），实测在 I/O 密集场景下约为串行的 1.7 倍速；
可在【设置 → 扫描选项】关闭「并行扫描」退回逐个扫描。此外首次扫描需要遍历大量目录（尤其 AppData 与 Program Files），
通常几分钟，也可关闭「大文件」「重复文件」扫描、调大「忽略小于 N MB」阈值进一步提速，并注意结果与串行完全一致。

**Q：删除几个 GB 的大文件时窗口显示"未响应"？**
A：v1.2.0 已修复。原因是日志与进度条每条都同步刷新控件、表格逐行重排重绘，主线程被高频 UI 操作占满。
现在日志/进度按 120ms 合并刷新、表格批量重建，删除大体积文件前也会在日志明确提示"体积较大，可能耗时较久，界面仍可操作"。
另外清理进行中会禁用 AI 识别（反之亦然），避免同一项目被并发改写。

**Q：exe 被 360 / 火绒报毒或拦截？**
A：这是 PyInstaller 单文件程序的常见**启发式误报**（"未知程序 / 未签名"），不是真病毒。v1.2.0 已做缓解：
① 禁用 UPX 压缩（最强误报特征）；② 写入完整的 exe 版本资源（公司名 / 产品名 / 版本号 / 描述）；
③ 附带应用图标；④ 构建时生成 `DiskCC.exe.sha256.txt`，接收方可用
`certutil -hashfile DiskCC.exe SHA256` 核对与发布方一致。
若仍被拦截，在 360/火绒里把该文件加入**白名单 / 信任区**即可（一般弹窗里有"允许运行/添加信任"选项）。
长期解决方案是对 exe 做代码签名证书签名，个人开发者可酌情购买或使用自签名证书。

**Q：清理后想还原？**
A：默认走回收站，去回收站还原即可；命令类项目（DISM、关闭休眠、删除还原点）属于系统配置变更，不可还原。

### v1.3.0
本版本对 v1.2.0 做了**全面回归测试**，覆盖模型/配置/AI/扫描引擎/清理器/CLI/历史/性能/界面共十一个维度；测试中复现并修复了 **12 处缺陷**（含 1 处高危安全缺口），全部以自动化断言固化（新增 **L 段（v1.3.0）回归断言**）。

**1. 扫描控制与进度**
- **并行扫描取消无效（高危体验缺陷）**：原 `_run_parallel` 用 `for f in futs: f.result()` 逐个阻塞等待，点「停止」后仍要等最慢的扫描器自然跑完（实测 3s 的扫描等满 3s 才停）。现改为轮询 `futures.wait(timeout=0.2)`，收到取消立即丢弃尚未开始的任务并尽快返回；已在运行的任务各自检查 `ctx.stopped()` 后退出。回归测试：取消响应 **≤0.5s**（修复前等满 3s）。
- **并行进度条倒退**：各扫描器子进度允许回退（如分段统计 80%→30%），原 `_dispatch` 直接覆盖总进度导致进度条倒退。现改为 `state[idx] = max(state.get(idx, 0.0), pct)`，整体进度单调不降。
- **单个扫描器构造失败拖垮整轮**：原 `[cls(ctx) for cls in SCANNERS]` 未捕获异常，任何一个扫描器初始化失败都会让整轮扫描崩溃、结果归零且错误列表为空。现实例化与 `enabled()` 判断均包 `try/except` 并记入 `ctx.error`，其余扫描器照常工作。

**2. 清理结果与列表一致性**
- **清理后按 path 误删同路径未勾选项（数据风险）**：目录项与文件模式项可能指向同一路径，原逻辑按 `path not in ok_paths` 剔除，会把**未勾选、根本没清理**的项目一并删掉。`CleanRecord` 新增 `item_id` 回连原 `ScanItem`，界面改为按 **id** 精确剔除。
- **演练模式项目从列表消失**：演练（`dry_run`）记录 `ok=True`，原逻辑按 ok 剔除了所有项目，让用户误以为已清理。现演练模式下**一个都不删、全部保留**并提示"本次未删除任何文件"。
- **重新扫描混入旧日志**：`start_scan` 只清空日志控件，不清空正在缓冲的 `_log_buf`，下一轮定时刷新时会把上轮残留日志带进来。现 `start_scan` 一并清空缓冲区。

**3. 安全校验（含一处高危缺口）**
- **右击「立即删除此项」绕过安全校验（高危）**：原分支直接调用 `fs.remove_dir_tree` / `force_remove_file`，**完全绕过 `Cleaner` 的校验**——受保护项（判定为已安装程序目录）、危险项、系统关键路径、允许范围外的路径都能被一键删掉，是全工具最危险的一处缺口。现改为走与批量清理**完全相同**的 `Cleaner.check_item` 统一校验：受保护/危险/系统路径弹「不能删除」；命令类项目（DISM/休眠/还原点）提示改走【🧹 清理选中】；其余才弹二次确认后永久删除。回归测试：受保护项被拦截且保留在列表、命令类项目提示而非直删。

**4. 界面状态与并发互斥**
- **忙碌时可打开设置**：`_set_busy` 此前未禁用【设置】按钮，但正在跑的这一轮已按旧配置启动（排除列表/体积阈值已在上下文缓存），改了只对下次生效。现忙碌时禁用设置按钮，避免"我明明加了排除怎么还在"的无解困惑。
- **AI 识别与扫描未互斥（v1.2.0 漏改）**：v1.2.0 只加了"清理×AI"互斥，漏掉"扫描×AI"。扫描线程仍在追加项目时识别完会重建整棵树，等扫描结束再覆盖一次，刚识别的项目就凭空消失。现已补上 `scan_worker.isRunning()` 判定。
- **关闭窗口后后台线程崩溃**：`closeEvent` 仅 `wait(2000)`，删除大文件/执行 DISM 时后台线程几秒退不出来（这里只等 2s），真正结束时 `emit` 到已销毁的控件导致关闭瞬间崩溃。现 `closeEvent` 先停刷新定时器、断开三个 worker 的 `progress/logged/finished` 信号，再停线程。
- **`_item_by_id` 线性查找卡顿**：勾选/右键/就地刷新/行选中都要按 id 反查，原实现 O(N) 线性扫描，数千项时一次「全选」就是几万次比较。现改为**索引查找**（整体替换 `items` 时失效重建），O(1)。

**5. 统计准确性**
- **扫描耗时统计偏差**：`ScanResult.finished_at` 始终为 0，界面显示的"耗时"实际是等到读取那一刻才算，扫描与展示之间有偏差。现 `run()` 末尾写入 `finished_at`，耗时统计准确。

**速度**
- **消除重复的目录递归**：扫描器们常在同一棵树里先后统计不同目录。现在一次遍历会顺带把走过的每个子目录体积写入缓存，后续请求直接命中。
- **并发单飞（single-flight）**：并行扫描时多个线程同时对同一目录求值原本会各算各的（这正是"并行反而比串行慢一倍"的根因之一）。后到的线程现在会等待并复用首个线程的结果。实测两模式下实际递归次数已完全一致（均为 12 次）。
- **去掉每个子项的一次 stat**：原先 `listdir + isdir(join(...))` 的写法要给每个子项多一次系统调用；改用 `os.scandir` 一次取回名称与类型（`fs.scan_dir / subdir_names / file_names`），在 Program Files / AppData / 浏览器缓存等遍历密集处收益最大。
- **`iter_files` 重写**：scandir + 预编译匹配，取代逐个文件调 `fnmatch`。
- **PE 版本采样**：原先无论是不是 PE 都先读满 1MB 再校验；现在先读 64KB 完成头部校验，非 PE 立即返回。**结论与旧实现已做逐个差分比对，完全一致。**

**稳定性**
- **进度信号节流**：扫描/清理会在每个小阶段回调进度，真实磁盘上动辄上万次跨线程投递，UI 线程忙于处理事件而表现为"扫描时界面卡住"。新增 `_Throttle`（最快 80ms 一次且进度至少变化 1% 才发射）作用于扫描与清理两个后台线程；最后是 100% 必定到达。
- 体积相关改动保持保守：可选瘦身开关默认关闭，避免未经 Windows 验证的裁剪进入默认产物。

**体积**
- `assets/logo.png`（约 1.4MB）实际从未被使用——`app_icon_path()` 以 `diskcc.ico` 优先，png 仅作兜底且无任何代码调用——**默认不再打进 exe**（源码里仍保留该图片素材，未做任何压缩或修改）。
- 新增**可选瘦身** `DISKCC_SLIM=1`：PySide6 的 hook 会把整个 `Qt/lib` 目录收集进产物，即便这些 Qt 模块已在 `excludes` 里被排除（Qml / Quick / Pdf / 虚拟键盘 / Wayland 等）。该开关会剔除这些原生库。
  - 用法：Linux/macOS `DISKCC_SLIM=1 pyinstaller DiskCC.spec`；Windows(cmd) `set DISKCC_SLIM=1 && pyinstaller DiskCC.spec`。
  - 现状：Linux 侧已验证剔除后可正常启动并跑通 `--cli` 完整扫描（-15.5% 体积）；因当前环境无法构建 Windows 产物，**Windows 侧依赖链尚未实测**，故默认关闭。建议你在 Windows 上构建一次瘦身版并双击确认能启动——若正常，下个版本可将其设为默认。

**测试与工具**
- 新增 `tests/bench.py`：构造确定性合成磁盘树，输出 `dir_size` / `iter_files` / 哈希微基准与全扫描耗时（默认取多轮最小值），用于后续版本的性能回归。
  `python tests/bench.py --rebuild --runs 5`
- `tests/full_test.py` 新增 **M 段（v1.3.2）17 项断言**，覆盖：scandir 分类助手、目录体积结果正确性、子树顺带缓存、并发单飞（结果与调用次数）、`iter_files` 与旧写法结果一致、PE 快速返回、进度节流行为、版本号与打包配置。全量 **161 项断言全部通过**。

**已知取舍**
- 并行扫描在本机合成树上仍慢于串行（0.535s vs 0.257s）：该环境数据全在页缓存，没有可重叠的真实磁盘等待，纯剩线程调度开销；真实 Windows 冷缓存 / 机械盘场景下并行仍应更优，故维持默认 `scan_parallel=True`。如你在实机上发现串行更快，可在设置里关闭并行扫描。
